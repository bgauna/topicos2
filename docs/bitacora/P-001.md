# P-001 — Análisis y especificación de requisitos

## 1. Rol

Actúa como un ingeniero de software senior especializado en análisis de requisitos, arquitectura de microservicios y Spec-Driven Development (SDD).

Formas parte del desarrollo de una plataforma de ticketera virtual para el Trabajo Final de Tópicos II — 2026.

Los responsables del proyecto son Briant + Fernando. Tu función es asistir en el análisis, documentación e implementación, sin asumir la autoría de las decisiones del equipo.

## 2. Contexto

La fuente principal de requisitos se encuentra en:

`docs/sources/trabajo-final-topicos-ii-2026.pdf`

Lee y analiza el documento completo antes de realizar cualquier modificación.

El proyecto se desarrollará utilizando Spec-Driven Development con OpenSpec, respetando las tres etapas incrementales establecidas en la consigna:

- Etapa I — Core.
- Etapa II — Integración con sistema de recomendación y caché.
- Etapa III — Escalabilidad.

Cada etapa corresponderá a un único change de OpenSpec.

Esta tarea corresponde a una fase preparatoria anterior a dichos changes y no implica implementar funcionalidades.

## 3. Stack tecnológico aprobado

Utiliza las siguientes tecnologías como contexto y restricciones del proyecto:

- JavaScript vanilla (ES6+).
- Node.js.
- Express.
- Vue 3 con Vite.
- PostgreSQL.
- Sequelize como ORM.
- NATS con JetStream.
- Redis.
- Docker y Docker Compose.
- JWT y bcrypt.
- Zod.
- OpenAPI y Swagger UI.
- Vitest y Supertest.
- Testcontainers.
- k6.
- Pino.
- Server-Sent Events (SSE).
- Git y GitHub.
- GitHub Actions.
- npm y npm Workspaces.
- ESLint y Prettier.
- OpenSpec.

No utilizar TypeScript, Drizzle ORM, Prisma ni React.

## 4. Decisiones previamente aprobadas

Las siguientes decisiones fueron aprobadas por los responsables del proyecto:

- DF-001: utilizar un simulador de pagos que permita representar pagos aprobados y rechazados.
- DF-002: establecer una duración inicial de reserva de 10 minutos, configurable.
- DF-003: utilizar JWT para autenticación.
- DF-004: controlar la asignación del rol Event Owner mediante administradores.
- DF-005: liberar el inventario correspondiente después de confirmar una devolución.
- DF-006: generar recomendaciones mediante reglas basadas en preferencias e historial de compras.
- DF-007: implementar colas independientes por evento con capacidad configurable.
- DF-008: utilizar PostgreSQL para la búsqueda avanzada y el ordenamiento por relevancia.
- DF-009: establecer objetivos de rendimiento medibles antes de ejecutar las pruebas de estrés.
- DF-010: desarrollar mockups e interfaces web mediante Vue.
- DF-011: mantener bases de datos independientes por servicio, utilizando inicialmente una misma instancia PostgreSQL.
- DF-012: utilizar Docker Compose como entorno de despliegue local.

Distingue estas decisiones de los requisitos explícitos de la consigna académica.

## 5. Objetivo

Crear un documento formal de requisitos en:

`docs/requirements.md`

El documento deberá constituir la fuente de referencia para la posterior creación de las especificaciones de OpenSpec.

## 6. Tareas

### 6.1. Análisis de la consigna

Identifica todos los requisitos explícitos del documento original.

Clasifícalos en:

- Requisitos funcionales.
- Requisitos no funcionales y técnicos.
- Restricciones metodológicas.
- Entregables académicos.

Conserva el significado original de cada requisito.

### 6.2. Identificación de actores

Documenta los actores del sistema:

- Administrador.
- Event Owner.
- Cliente.

Describe sus responsabilidades, permisos y restricciones.

Cuando un permiso no esté explícitamente definido, identifícalo como una propuesta pendiente de validación.

### 6.3. Requisitos funcionales

Asigna identificadores únicos y estables utilizando el formato RF-XXX.

Incluye como mínimo:

- Identidad y autenticación.
- Autorización por roles.
- Gestión y publicación de eventos.
- Gestión de zonas y asientos.
- Tickets numerados y no numerados.
- Reservas y compras.
- Prevención de doble venta.
- Idempotencia.
- Devoluciones.
- Recomendaciones personalizadas.
- Búsquedas por múltiples criterios.
- Colas de venta para eventos masivos.
- Notificación de posición en cola.

Distingue los requisitos explícitos, los derivados necesarios y las decisiones aprobadas.

### 6.4. Requisitos no funcionales

Asigna identificadores RNF-XXX.

Considera:

- Seguridad.
- Integridad y consistencia de datos.
- Concurrencia.
- Escalabilidad.
- Tolerancia a fallos.
- Observabilidad.
- Registro HTTP con medición de tiempos.
- Rendimiento.
- Estrategias de caché.
- Despliegue independiente de servicios.
- Mantenibilidad.
- Testabilidad.
- Reproducibilidad del entorno.

No inventes objetivos cuantitativos de rendimiento.

### 6.5. Reglas de negocio

Asigna identificadores RN-XXX.

Identifica las reglas necesarias para garantizar:

- Un asiento no puede tener dos ventas activas simultáneas.
- Una zona no puede vender más entradas que su capacidad.
- Una solicitud repetida no debe generar compras duplicadas.
- Una reserva vencida debe liberar el inventario correspondiente.
- Una devolución confirmada debe liberar inventario una única vez.
- Los Event Owners deben operar únicamente sobre los eventos para los que estén autorizados.
- El acceso a operaciones restringidas debe depender del rol del usuario.
- Las solicitudes de venta masiva deben respetar el orden definido para la cola.

Clasifica las reglas según su origen y registra las ambigüedades que requieran aprobación.

### 6.6. Criterios de aceptación

Define criterios de aceptación verificables para cada requisito funcional y, cuando corresponda, para los requisitos no funcionales.

Utiliza escenarios expresados mediante el formato:

- DADO un contexto inicial.
- CUANDO ocurre una acción.
- ENTONCES se obtiene un resultado esperado.

Incluye escenarios exitosos, alternativos, de error y de concurrencia cuando sean relevantes.

### 6.7. Matriz de trazabilidad

Construye una matriz que contenga:

- Identificador.
- Nombre del requisito.
- Clasificación.
- Origen.
- Página o sección de la consigna, cuando corresponda.
- Etapa de implementación.
- Identificadores de criterios de aceptación asociados.

Utiliza las siguientes categorías de origen:

- CONSIGNA: requisito explícito del PDF.
- DERIVADO: requisito necesario para satisfacer otro requisito.
- DECISIÓN APROBADA: decisión proporcionada por los responsables.
- PROPUESTA: sugerencia pendiente de validación.

### 6.8. Distribución incremental

Distribuye los requisitos respetando las tres etapas oficiales:

**Etapa I — Core**

Backend, APIs, autenticación, gestión de eventos, compra de tickets, integridad de inventario, concurrencia, idempotencia, bitácora HTTP y mockups.

**Etapa II — Recomendaciones y caché**

Recomendaciones personalizadas, integración entre servicios y estrategias de caché.

**Etapa III — Escalabilidad**

Colas de venta, notificaciones, devoluciones, búsqueda avanzada y pruebas de estrés.

Identifica dependencias entre requisitos y etapas.

### 6.9. Ambigüedades y riesgos

Identifica requisitos incompletos, ambiguos o contradictorios.

Para cada ambigüedad indica:

- Descripción.
- Impacto potencial.
- Alternativas posibles.
- Recomendación.
- Estado pendiente de aprobación.

No presentes una recomendación nueva como una decisión ya aprobada.

### 6.10. Entregables académicos

Documenta los entregables establecidos en la consigna:

- CONTRIBUTE.md.
- Changes archivados con specs, design y tasks.
- Mockups.
- APIs funcionales.
- Tests de unidad.
- Bitácora de documentación.

## 7. Estructura del documento

Organiza `docs/requirements.md` de la siguiente manera:

1. Información del proyecto.

## 9. Criterios de finalización

La tarea se considera completada cuando:

- Existe el archivo `docs/requirements.md`.
- Todos los requisitos explícitos de la consigna se encuentran representados.

Al finalizar, presenta:

Detente al finalizar esta tarea y espera la revisión de los responsables. No avances a la arquitectura ni a la implementación.
