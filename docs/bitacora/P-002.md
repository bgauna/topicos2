### Arquitectura propuesta

| Etapa | Componentes, responsabilidades y bases de datos |
| --- | --- |
| **I · Core** | Web Vue y API Gateway sin base de negocio propia. Identity gestiona cuentas, roles y JWT en `identity_db`. Catalog gestiona eventos y publicación en `catalog_db`. Ticketing controla inventario, reservas, pagos simulados, compras y tickets en `ticketing_db`. PostgreSQL y NATS JetStream sostienen la persistencia y la publicación recuperable. |
| **II · Recomendaciones y caché** | Recommendations posee preferencias y proyecciones en `recommendations_db`. Redis aloja copias Cache-Aside. PostgreSQL sigue siendo la fuente de verdad del inventario. |
| **III · Escalabilidad** | Waiting Room posee entradas y turnos en `waiting_room_db` y notifica posición mediante SSE. Ticketing verifica el turno en la ruta de venta e incorpora devoluciones. Catalog suma búsqueda avanzada. k6 se reserva para las pruebas de estrés de esta etapa. |

La propuesta mantiene las invariantes de venta en transacciones locales de Ticketing y separa la publicación de un evento de su habilitación efectiva para vender. El cierre se confirma en Ticketing antes de que Catalog lo dé por aplicado. Para la sala de espera, la asignación FIFO de turnos y el procesamiento ordenado tienen garantías y verificaciones separadas.

Se evaluaron un monolito modular, una base de datos compartida y servicios separados para pagos, reservas e inventario. La propuesta favorece microservicios por capacidad porque permiten demostrar el despliegue independiente y conservan la integridad de la venta dentro de un único propietario.
