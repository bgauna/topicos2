# ADR-004 — Propiedad y aislamiento de datos

- Estado: Propuesto
- Fecha de elaboración: 2026-11-25
- Autores: Briant + Fernando
- Etapa de aplicación: I–III
- Requisitos relacionados: RF-025, RNF-004, RNF-007, RNF-014, RNF-018, RNF-021

## Contexto

Se necesitan datos transaccionales verificables y lectura derivada sin acoplar los modelos de persistencia.

## Fuerzas y restricciones

DF-011 aprueba bases por servicio dentro de una instancia inicial. AMB-005 exige PostgreSQL como verdad transaccional y un dueño por dato.

## Alternativas consideradas

Una base y esquema compartidos facilitan joins y vuelven inseparables las migraciones. Instancias separadas refuerzan aislamiento operativo con mayor costo. Bases separadas en una instancia satisfacen el aislamiento lógico inicial.

## Decisión propuesta

Proponer `identity_db`, `catalog_db`, `ticketing_db`, `recommendations_db` y `waiting_room_db` según sus etapas. Cada servicio usa credenciales exclusivas y versiona y aplica sus migraciones. Evitar acceso SQL ajeno, foreign keys entre bases y modelos Sequelize compartidos. Usar identificadores estables, API o proyección explícita. Conservar importes y moneda históricos en la compra. Documentar instantes UTC y zona IANA según [propiedad](../data-ownership.md).

## Justificación

El dato se cambia donde reside su regla. Consumo de proyecciones y referencias no modifica la autoridad propietaria.

## Consecuencias positivas

Permite evolucionar esquemas y recuperar proyecciones con límites auditables.

## Consecuencias negativas

Las consultas entre dominios requieren composición o proyecciones. La instancia comparte recursos y disponibilidad.

## Riesgos y mitigaciones

Otorgar permisos mínimos por base y revisar migraciones compatibles. Probar aislación de credenciales, precio histórico y fechas de frontera.
