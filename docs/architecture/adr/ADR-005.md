# ADR-005 — Comunicación HTTP y NATS JetStream

- Estado: Aceptado
- Fecha de elaboración: 2026-11-25
- Autores: Briant + Fernando
- Etapa de aplicación: I–III
- Requisitos relacionados: RNF-005, RNF-006, RNF-007, RNF-010, RNF-011, RNF-022, RF-021

## Contexto

La operación inmediata debe conocer su resultado y proyecciones y notificaciones pueden tolerar retrasos.

## Fuerzas y restricciones

El stack fija Express y JetStream. AMB-005 exige comunicación persistente cuando haga falta, consumidores idempotentes y consistencia eventual acotada.

## Alternativas consideradas

Solo HTTP obliga al productor a esperar estados de lectura secundarios. Solo mensajería complica decisiones inmediatas y contratos de usuario. Una combinación de REST y JetStream separa cada necesidad.

## Decisión propuesta

Proponer REST para consultas y comandos que exigen respuesta. Usar JetStream para eventos de hechos ya confirmados, transporte durable, publicación desde outbox, ACK explícito después del efecto y versionado. Usar SSE para posición en III. Mantener timeouts, errores y reintentos seguros de [comunicación](../communication.md).

## Justificación

El resultado de compra depende del commit local. La mensajería recuperable tolera desconexiones de datos derivados.

## Consecuencias positivas

Reduce dependencias temporales y facilita replay, integración progresiva y seguimiento de eventos.

## Consecuencias negativas

Requiere gestionar compatibilidad, retención, mensajes repetidos o desordenados, fallos ambiguos y datos atrasados.

## Riesgos y mitigaciones

Usar Event ID estable y revisión monotónica de agregado. JetStream no asegura un único efecto ni FIFO de negocio con consumidores concurrentes. En III, mantener la secuencia de negocio en los propietarios y controlar el avance.
