# ADR-002 — Monorepo y npm Workspaces

- Estado: Aceptado
- Fecha de elaboración: 2026-11-25
- Autores: Briant + Fernando
- Etapa de aplicación: I–III
- Requisitos relacionados: RNF-008, RNF-015, RNF-016, RNF-017, RM-003

## Contexto

Un equipo pequeño comparte cambios de contratos y operaciones, con servicios que requieren su propio despliegue.

## Fuerzas y restricciones

Usar npm Workspaces, JavaScript y Git aprobado. Separar dependencias de construcción, contratos, persistencia y lógica de negocio.

## Alternativas consideradas

Repositorios independientes permiten versionar cada servicio con mayor aislamiento, a cambio de coordinación y duplicación de CI. Un monorepo sin workspaces tiende a replicar verificación y resolución de dependencias. Workspaces centraliza el lockfile con manifiestos propios.

## Decisión propuesta

Proponer la siguiente estructura conceptual. Los nombres se incorporan cuando corresponda a su etapa.

| Ruta | Responsabilidad |
| --- | --- |
| `apps/api-gateway/`, `apps/web/` | Fachada Express y frontend Vue. |
| `services/identity/`, `services/catalog/`, `services/ticketing/` | Servicios del Core. |
| `services/recommendations/`, `services/waiting-room/` | Servicios de II y III, respectivamente. |
| `packages/contracts/` | Esquemas de intercambio y tipos de datos de contratos expresados en JavaScript u OpenAPI, validables con Zod cuando corresponda. |
| `infra/`, `docs/`, `openspec/` | Infraestructura por entorno, documentación y especificaciones. |
| `tests/load/`, `.github/workflows/` | Pruebas k6 de III y automatización CI. |

Aplicar por servicio rutas y controladores HTTP, casos de uso, reglas de negocio, repositorios, modelos Sequelize, migraciones, configuración, mensajería y pruebas. Agrupar responsabilidades simples cuando una capa adicional aporte solo reenvío. Cada servicio declara dependencias y se verifica por separado. El workspace de contratos excluye lógica de negocio, modelos, migraciones, acceso a datos y configuración de servicios.

## Justificación

Los manifiestos propios y contratos de intercambio versionados permiten pruebas coordinadas con artefactos desplegables por separado.

## Consecuencias positivas

Ofrece revisión conjunta de contratos, instalación reproducible y cambios incrementales por workspace.

## Consecuencias negativas

El lockfile común y los módulos compartidos pueden acoplar builds o ampliar el alcance de un cambio.

## Riesgos y mitigaciones

Restringir importaciones entre servicios a contratos publicados y comprobar compilación o arranque aislado. Usar cambios compatibles para despliegues escalonados.

## Validación

CA-RNF-008-01, CA-RNF-015-01, CA-RNF-016-01. Verificar consumo de contratos sin importar módulos privados y despliegue por servicio.

## Decisiones previas relacionadas

DF-011, DF-012; [ADR-001](ADR-001.md), [ADR-003](ADR-003.md), [ADR-011](ADR-011.md).

## Definiciones diferidas

Definir nombres de paquetes, comandos, estrategia de publicación, política de dependencias y estructura mínima del Core antes del scaffolding.
