# ADR-011 — Testing e integración continua

- Estado: Propuesto
- Fecha de elaboración: 2026-11-25
- Autores: Briant + Fernando
- Etapa de aplicación: I–III
- Requisitos relacionados: RNF-002, RNF-012, RNF-016, RNF-017, RNF-019, RNF-022, RM-003, EA-005

## Contexto

La validación de reglas y contratos necesita ejecución rápida y pruebas contra las infraestructuras que sostienen las garantías.

## Fuerzas y restricciones

El stack aprueba Vitest, Supertest, Testcontainers, k6 y GitHub Actions. DF-009 exige fijar condiciones y objetivos de estrés antes de ejecutar. No hay porcentajes de cobertura ni umbrales cuantitativos aprobados.

## Alternativas consideradas

Solo mocks y base en memoria permiten iteración rápida, pero no evidencian bloqueos, aislamiento, constraints y reentregas reales. Solo end-to-end dificulta diagnóstico y velocidad. Una combinación por capas cubre ambos aspectos.

## Decisión propuesta

Usar Vitest para reglas, transformaciones y casos de uso con dobles de límites controlados. Usar Supertest para contratos HTTP, errores y permisos. Ejecutar integración con PostgreSQL y NATS con JetStream reales mediante Testcontainers, y Redis real cuando se pruebe caché en II. Verificar contratos, compatibilidad de versiones y OpenAPI, ESLint y Prettier en GitHub Actions. En III ejecutar k6 con plan previo de carga, entorno, duración, umbrales y evaluación de throughput, p95, p99, errores, cola, espera e integridad. Verificar antes de archivar cada change.

## Justificación

Se prueban determinísticamente las reglas unitarias y se valida en infraestructura real lo que depende de concurrencia, deduplicación, transporte y reinicios.

## Consecuencias positivas

Ofrece evidencia reproducible por etapa y permite identificar regresiones de reglas y contratos antes de despliegue.

## Consecuencias negativas

Los contenedores y pruebas concurrentes elevan tiempo de CI y necesitan aislamiento y sincronización controlada.

## Riesgos y mitigaciones

Coordinar carreras con barreras de prueba en vez de esperas arbitrarias. Usar bases aisladas y reloj controlado para transiciones, medir resultados en la base y forzar fallos de NATS y consumidor. Proponer ejecuciones separadas para estrés, con condiciones versionadas.
